# 安全模型

[English](../security.md) | **简体中文**

## 保护目标

- 恶意网络响应必须拥有配置公钥生成的合法 RSA-SHA256 签名，才能执行 JavaScript。
- 被篡改的启动 bundle 或资源文件会因 SHA-256 校验失败被拒绝。
- 路径穿越、重复路径、超大响应、runtime、platform 或 channel 不匹配的更新
  都会在安装前被拒绝。
- 下载不完整的更新不会在启动时被选中。
- 启动失败循环会自动回退到上一 known-good 版本或内置 bundle。

## 密钥管理

- 至少使用 RSA-3072，CLI 默认即 3072。
- App 中只能包含 SPKI 公钥。
- 私钥不得进入仓库，应保存在 Secret Manager 或 HSM 中。
- 管理端 Token 必须具有高熵，并与签名密钥分开轮换。
- 发布记录需要保存 key ID。协议 v1 客户端只信任一个内置公钥，因此轮换公钥
  需要发布一个信任新公钥的原生 App。

## 传输安全

生产环境必须使用 HTTPS。Android 只有在显式开启并限定本地开发主机时才允许
HTTP 明文。iOS 只允许在 Debug 构建中通过 `HotfixAllowCleartext` 使用回环 HTTP。

TLS 保护可用性和隐私；清单签名则在 CDN 或源存储被攻破时继续保护代码完整性。

## 公开生产前仍需加固

当前参考服务端是单节点实现。公开暴露前至少需要：

- 在边缘层鉴权并限流所有管理接口和检查接口；
- 使用可信证书终止 TLS；
- 以非特权用户运行，并尽量使用只读根文件系统；
- 将不可变更新文件放在 CDN 后面；
- 监控签名失败、哈希失败、回滚激增和发布异常；
- 备份发布元数据，并用 HSM/KMS 保护私钥；
- 将本地 channel 文件替换为事务性的多节点存储；
- 增加 request ID、结构化审计日志和保留策略；
- 对原生代码进行独立安全审查。

不要把私钥、管理端 Token、Source Map 或签名环境放入移动 App。

## 商店与法律政策

热更新不能绕过应用商店的分发要求。生产启用前必须审查 Apple App Store 和
Google Play 对可执行代码、信息披露和更新行为的规定。
